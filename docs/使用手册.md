# ARTEX 使用手册：从第一次启动到熟练使用

这套手册面向第一次接触 ARTEX 的使用者。先把页面打开、配置一个可用模型，再完成一个小任务；遇到需要调整的地方，再查后面的配置章节。不需要先读懂项目架构，也不需要一开始就配置 MCP、通知或自定义 Agent。

说明依据当前仓库的界面、配置文件和后端实现编写。旧版本的按钮和功能可能不同，请同时核对「系统配置 → 版本与更新」中的版本。示例仅用于项目 README 规定的本地隔离学习与验证场景，使用范围见 [许可与免责声明](https://github.com/fraternity-z/ARTEX#许可与免责声明)。

<a id="concepts"></a>

## 1. 先认识几个词

可以把 ARTEX 理解为一个有任务看板、工具箱和记录员的 AI 工作台。

| 名称 | 通俗解释 |
| --- | --- |
| LLM / 模型配置 | AI 的连接信息：接口格式、模型名、服务地址和 API Key |
| Agent | 有明确分工的 AI 角色。Planner 负责规划，Worker 执行具体工作，主 Agent 供你沟通和干预 |
| 任务 | 一次有明确描述、目标和范围的工作；不是一次聊天消息 |
| 意图（Intent） | Planner 拆出的一项具体工作，由 Worker 领取执行 |
| 事实（Fact） | 执行中已经观察到、写入记录的结果 |
| 提示（Hint） | 待进一步确认的线索；不等于已确认漏洞 |
| 发现（Finding） | 独立保存的漏洞记录，含评级、处置状态、报告和证据 |
| 资产 | 域名、IP、服务、应用、接口等对象。资产库全局共享，任务记录自己的测试范围 |
| 探索链路 | “为什么做这项工作、基于什么事实、产生什么结果”的关系图 |
| 流量 | 经录制代理捕获的 HTTP 请求和响应；与发给模型的 LLM 请求是两类记录 |
| Token | 模型处理文本的计量单位。输入、输出、重试和报告生成都可能产生用量 |
| MCP / Skill / 工具 | MCP 接外部工具服务；Skill 提供使用方法和配套文件；工具执行具体操作 |

## 2. 选择启动方式

| 方式 | 需要准备 | 适合谁 |
| --- | --- | --- |
| Mock 界面演示 | Git、Node.js 22、npm | 只想了解操作界面；模拟数据，不执行真实任务 |
| Docker Compose | Git、可用的 Docker Engine 和 Compose | 首次完整使用；数据库和工具环境较省心 |
| Release 二进制 | 已发布的对应平台程序包、PostgreSQL、需要使用的外部工具 | 不想安装 Go / Node 构建环境的人 |
| 源码运行或编译 | Go 1.26.3 或满足 `go.mod` 要求的工具链、Node.js 22、npm、PostgreSQL | 开发者，或尚无可用发布包时 |

Compose 使用 PostgreSQL 16。项目没有给出统一的最低内存承诺：任务数量、Worker 并发、浏览器和流量保存量都会影响资源需求。先用一个任务、少量并发确认可用，再按资源和模型限额增加。

**镜像和二进制是否可下载，以本仓库 [Releases](https://github.com/fraternity-z/ARTEX/releases) 和 GHCR 实际发布结果为准。** 历史 Git 标签不一定有对应程序包。拉取提示找不到镜像时，先确认是否已发布；未发布时使用[源码方式](部署维护与排错.md#source)。

<a id="mock"></a>

### 2.1 只体验界面

在仓库根目录开始。此方式不需要 PostgreSQL 和模型密钥。

Linux / macOS / WSL：

```bash
git clone https://github.com/fraternity-z/ARTEX.git
cd ARTEX/web
npm ci
NEXT_PUBLIC_MOCK=1 npm run dev -- --port 5173
```

Windows PowerShell：

```powershell
git clone https://github.com/fraternity-z/ARTEX.git
Set-Location ARTEX/web
npm ci
$env:NEXT_PUBLIC_MOCK = "1"
npm run dev -- --port 5173
```

打开 [http://localhost:5173](http://localhost:5173)。终端保持运行，按 `Ctrl+C` 退出。PowerShell 下退出后执行 `Remove-Item Env:NEXT_PUBLIC_MOCK`，避免同一终端下一次仍启动模拟界面。

**成功标志：** 能看到模拟任务、资产等演示内容。这里的操作不能证明数据库、模型和执行工具已就绪，也不要把真实密钥填入演示。

<a id="docker"></a>

### 2.2 用 Docker Compose 启动完整系统

以下命令均在克隆后的 `ARTEX` 目录执行。Windows 使用 Docker Desktop 的 Linux 容器环境；Linux 使用已经启动的 Docker Engine。

**第一步：检查 Docker。**

```text
docker version
docker compose version
```

`docker version` 应能显示服务端信息。只有客户端、提示连接不到 daemon 时，先启动 Docker。

**第二步：取得项目并准备配置。**

```text
git clone https://github.com/fraternity-z/ARTEX.git
cd ARTEX
```

Linux / macOS / WSL：

```bash
cp .env.example .env
```

Windows PowerShell：

```powershell
Copy-Item .env.example .env
notepad .env
```

使用文本编辑器修改 `.env`：

```dotenv
ARTEX_IMAGE=ghcr.io/fraternity-z/artex
ARTEX_TAG=latest
POSTGRES_USER=artex
POSTGRES_PASSWORD=替换为你生成的随机密码
POSTGRES_DB=artex
```

不要原样保存中文占位符，也不要使用示例默认密码。新手可生成至少 24 位大小写字母与数字组合的随机密码，避免 Compose 拼接数据库 URL 时遇到 `@`、`:`、`/`、`#` 等字符转义问题。`POSTGRES_PASSWORD` 是**数据库密码**，稍后设置的 ARTEX 登录密码与它不同。

`ANTHROPIC_API_KEY`、`OPENAI_API_KEY` 和 `ARTEX_LLM_*` 可以先留空，进入页面后再配置。`.env` 包含秘密信息，不要发到 Issue 或提交到 Git。

**第三步：启动并确认状态。**

```text
docker compose up -d
docker compose ps
docker compose logs --tail=100 artex
```

首次需要下载镜像，时间取决于网络。预期 PostgreSQL 显示健康，ARTEX 持续运行而非反复重启。

健康检查（Windows 请用 `curl.exe`）：

```bash
curl --fail http://127.0.0.1:8787/api/health
```

**第四步：打开页面。**

在浏览器访问 [http://localhost:8787](http://localhost:8787)。如果部署在另一台机器，浏览器中的 `localhost` 指你的电脑，应改成那台机器可访问的地址。首次初始化期间应限制访问来源，先由自己设置密码。

Compose 默认映射网页端口 `8787`；流量代理 `8788` 仅映射到宿主机回环地址；数据库没有对宿主机发布端口。完整的端口和访问限制说明见[部署维护与排错](部署维护与排错.md#ports)。

**第五步：知道数据在哪里。**

| 位置 | 保存什么 |
| --- | --- |
| PostgreSQL 的 Compose 卷 `pgdata` | 任务、资产、发现、用户设置、模型配置等主要数据 |
| 仓库下的 `data/` | 工作文件、流量、证据正文和任务归档等文件数据 |
| 仓库下的 `skills/` | 挂载进容器的技能文件 |
| `.env` | Compose 启动参数和数据库密码 |

浏览器登录签名文件 `jwt.key` 当前位于可执行文件旁；容器里是 `/app/jwt.key`，不在默认挂载的 `data/` 内。重建容器后可能需要重新登录，不代表任务数据丢失。完整备份应同时考虑数据库、文件和配置，见[备份与恢复](部署维护与排错.md#backup)。

日常启停：

```text
docker compose stop
docker compose start
```

`stop` 不删除容器和数据。**不要把 `docker compose down -v` 当成普通停止命令，它会删除数据库卷。**

<a id="setup"></a>

## 3. 首次设置：账号、模型、最小配置

### 3.1 初始化登录密码

首次访问会进入 `/setup`。设置至少 8 位密码并确认，保存后自动登录。后续登录用户名固定为 **`ARTEX`（大写）**。

登录后可通过侧边栏底部用户菜单修改密码。已有实例应直接进入登录页；如果出现「无法确认初始化状态」，先排查后端与数据库，不要通过删除数据库或登录设置来“重新初始化”。

### 3.2 添加并激活一个模型

1. 在侧边栏「系统」分组点击 **LLM**，进入「模型配置」。
2. 新增配置，填写名称，例如「本地练习模型」。
3. 按服务商实际支持的协议选择格式：`Anthropic`、`OpenAI (Chat Completions)` 或 `OpenAI (Responses API)`。
4. 填写服务商提供的模型 ID 和 API Key。模型展示名称不一定是可调用的 ID；需要时使用页面的加载模型功能，但网关不支持模型列表时也可手填。
5. 使用兼容网关时，填写其要求的 Base URL。它是 API 基础地址，不是网页聊天地址，也不要擅自拼接 `/chat/completions` 或 `/responses`。
6. 不确定的思考参数、输出上限、限速和重试覆盖先保持默认；上下文窗口应与实际模型能力匹配。
7. 点击连接测试，成功后**保存**。回到列表，**激活**这份配置，确认激活标记。

连接测试会调用模型，可能产生少量费用。测试成功只证明这组参数在测试请求中可用，不保证模型工具调用、长上下文或所有高级参数都兼容。

**成功标志：**「对话」页能选择可用 Agent，发送“请用一句话介绍你的职责”并收到回复。只在对话里测试，不必立即创建复杂任务。

如果改了全局模型，某个 Agent 仍用旧模型，检查它是否绑定了独立配置。实际优先级是 **Agent 绑定 → 任务配置链或会话指定 → 全局激活配置**。详见[模型选择与故障转移](高级配置.md#llm)。

### 3.3 第一次建议这样设置

打开「系统配置」，先只调整你确实需要的选项：

| 选项 | 第一次的建议 | 原因 |
| --- | --- | --- |
| 并发工作 Agent 数 | 先设为 `1`，熟悉后再增加；产品默认 `3` | 更容易观察执行，减少并发请求；对之后启动的任务生效 |
| 流量捕获 | 离线文件练习可关闭；要留 HTTP 证据时在任务前开启 | 默认关闭，无法补录过去的请求 |
| Agent 自动绑定流量 | 先保持关闭，学会人工关联后再开启 | 默认关闭；与捕获是独立功能，开启会增加模型用量 |
| 网络搜索 | 保持关闭 | 第一个本地练习不需要联网搜索 |
| 全局代理 | 无明确需要就留空 | 错误代理会影响目标请求；模型代理单独配置 |
| 操作约束注入 | 保持 Planner、Worker 都开启 | 让后续规划和执行看到你写的约束 |
| noa 上下文压缩 | 保持关闭 | 实验选项，先使用原有压缩机制 |

<a id="first-task"></a>

## 4. 第一个练习：离线文件检查

先用一个不访问任何目标的练习，确认“上传 → 规划 → 工具读取 → 记录结果”完整跑通。**这个练习不保证产生漏洞；能得到有依据的结论就是成功。**

### 4.1 准备一个练习文件

在自己的电脑创建 `lab-response.txt`，内容如下。它只是虚构 HTTP 响应，不含真实用户数据：

```http
HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8
Cache-Control: no-store

<!doctype html><title>Local learning page</title><h1>Hello ARTEX</h1>
```

### 4.2 创建任务

进入「任务 → 新建任务」，填写：

**名称：** `第一次练习：离线响应检查`

**描述：**

```text
本次只分析我上传的 lab-response.txt。它是本地学习用的虚构 HTTP 响应。
允许读取附件，解释响应头和正文。
禁止访问网络、执行扫描、修改文件或安装依赖。
请将“文件中直接观察到的事实”和“缺乏上下文无法确认的事项”分开记录。
```

**目标：**

```text
读取附件，解释状态码、Content-Type、Cache-Control，并给出简明检查结论。
不要把响应头缺失直接判定为已确认漏洞；没有足够证据就说明无法判断。
完成文件分析和结果记录后结束任务。
```

然后：

1. 点击「上传文件」，选择 `lab-response.txt`，确认文件路径已追加到描述末尾。保留这段路径，Agent 依靠它读取附件。
2. 「LLM 配置链」可留空，跟随已配置的 Agent / 全局模型。
3. 关联任务、企业、计划启动均留空。
4. 展开「高级设置」，任务超时可设为 `10` 分钟；其余保持默认。
5. 点击「创建」，返回列表后进入这条任务。

通常创建后会启动；启用了计划或任务并发限制时，也可能处于等待窗口或排队状态。超时会触发收尾，不保证恰好在第 10 分钟那一秒停止所有工作。

### 4.3 观察并验收

1. **会话：** 查看 Planner 和 Worker 的运行记录。展开工具调用，确认读取了正确文件。
2. **总览：** 检查目标和操作约束，确认没有把练习理解成联网测试。
3. **播报板 / 探索链路：** 看已经写入的事实和工作关系。
4. **报告：** 查看当前任务的汇总。若暂无报告，先看任务与报告 Agent 的实际运行情况。
5. 出现审批时，阅读具体工具与参数后再决定；需要整个任务停下来时使用顶部「暂停」。

完成标准：附件被成功读取；结论能对应文件内容；没有进行禁止的联网操作；知道如何找到执行记录和暂停任务。新手阶段不用追求发现数量、覆盖率或复杂工具链。

### 4.4 下一步：本地隔离实验服务

准备好自己的隔离实验服务后，把任务描述换成**从 ARTEX 执行环境实际可访问的地址**，写清允许访问的单个服务、允许的验证方法和结束标准。先验证一个页面或接口，不要把目标写成“尽可能发现一切”。

Docker 里的 `127.0.0.1` 指 ARTEX 容器，不是宿主机。Docker Desktop 可根据实际网络配置使用 `host.docker.internal`；Linux Docker 需要另行配置宿主机入口或让实验服务加入合适的容器网络。服务还必须监听对应接口。不要因为访问失败就把整个本地网络加入范围。

操作约束是发给模型的指令，不是操作系统级沙箱。需要限制执行能力时，同时使用任务资产允许规则、工具绑定和审批设置；见[范围与拦截](高级配置.md#intercept)。

## 5. 常用页面速查

| 页面 | 什么时候打开 |
| --- | --- |
| 仪表盘 | 看总体任务情况、Token 用量和活动 |
| 对话 | 与某个 Agent 独立交流；不等于新建扫描任务 |
| 任务 | 创建、查看、暂停、恢复、分类和归档任务 |
| 计划任务 | 设置任务的开始、暂停与恢复时间窗口 |
| 发现 | 审核漏洞、修改处置状态、归并、复测和导出 |
| 流量 | 查 HTTP 请求/响应，并把证据关联到漏洞 |
| 工具执行 | 找某次工具调用的输入、输出和错误 |
| LLM 录制 | 按需记录并检查模型请求/响应，帮助排查模型问题 |
| 资产 / 资产同步 | 维护企业和资产，从 ScopeSentry 导入数据 |
| 工作空间 | 查看、上传和编辑服务器上的工作文件 |
| LLM / Agent / MCP / Skill / 工具 | 管理模型与执行能力 |
| 拦截规则 / 资产拦截 / 审批记录 | 配置规则并处理被拦下的操作 |
| 通知推送 | 配置通知渠道、过滤条件和查看投递结果 |
| 日志 / 系统配置 | 排查后端问题，调整运行设置和更新版本 |

接下来按实际工作顺序阅读[日常使用](日常使用.md)。如果卡在启动或登录阶段，直接查[故障排查](部署维护与排错.md#troubleshooting)。
