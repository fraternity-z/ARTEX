## 1. 端口与访问方式

| 端口 | 用途 | 当前默认行为 |
| --- | --- | --- |
| 8787 | ARTEX 网页与 API | 二进制默认 `:8787`；Compose 映射 `8787:8787` |
| 8788 | HTTP 流量录制代理 | 普通二进制监听 `127.0.0.1:8788`；Compose 只向宿主回环映射 |
| 5432 | PostgreSQL 容器内部端口 | 默认 Compose 不映射到宿主机 |
| 5433 | 文件示例采用的本地 PostgreSQL 端口 | 不是所有安装的默认值，需要和实际映射核对 |
| 5173 | 本手册明确指定的前端开发端口 | 裸 `npm run dev` 未固定此端口，通常从 3000 启动，以终端输出为准 |

**网页端口与代理端口不是一回事。** 不要在浏览器打开 8788 来寻找管理界面，也不要把 8787 当 HTTP 出口代理。

只在本机使用时，可把 Compose 的网页映射编辑为：

```yaml
ports:
  - "127.0.0.1:8787:8787"
  - "127.0.0.1:8788:8788"
```

这是替换原 `artex.ports` 列表的片段，不是一份完整 Compose 文件。修改后 `docker compose up -d artex` 应用；单纯 `restart` 不会重新加载容器环境与端口定义。

如果用覆盖文件改端口，要确认 Compose 合并后的端口没有保留额外公开映射。可以用 `docker compose config --quiet` 检查结构；完整 `docker compose config` 会展开环境变量，输出可能含密码，不要直接贴到 Issue。

## 2. Release 二进制部署

### 2.1 下载正确程序包

到本仓库 [Releases](https://github.com/fraternity-z/ARTEX/releases) 选择实际已发布版本，按系统与 CPU 下载：

| 系统 | 常见架构 | 包名中的平台部分 |
| --- | --- | --- |
| Linux x86_64 | Intel / AMD 64 位 | `linux-amd64` |
| Linux ARM64 | ARM64 Kali、ARM 服务器等 | `linux-arm64` |
| macOS Intel | x86_64 | `darwin-amd64` |
| macOS Apple Silicon | arm64 | `darwin-arm64` |
| Windows 64 位 | amd64 | `windows-amd64` |

包名形如 `artex-<版本>-<平台>.zip`，不要把示例版本号当成已有 Release。下载对应 `SHA256SUMS` 并比对 SHA-256，确认文件完整后解压。

Linux 在下载目录可用：

```bash
sha256sum --ignore-missing --check SHA256SUMS
```

macOS 可用 `shasum -a 256 <压缩包文件名>` 计算后与清单对应行比对；Windows 使用：

```powershell
Get-FileHash -Algorithm SHA256 .\artex-实际版本-windows-amd64.zip
```

### 2.2 配置数据库与技能目录

进入解压后的程序目录。Linux / macOS：

```bash
cp config.example.json config.json
```

Windows PowerShell：

```powershell
Copy-Item .\config.example.json .\config.json
notepad .\config.json
```

按[配置说明](高级配置.md#config)填写可连接的 PostgreSQL；特别核对端口和 `skill_dir`。数据库服务需要你提前准备，应用会在启动时处理所需 schema。`database` 不包含 SQLite 的替代模式，主业务数据必须有 PostgreSQL。

包内有应用、对应平台启动脚本、`skills/`、配置示例和 README。程序包不等于 Docker 工具环境：Bash、Python、浏览器或其他工具是否存在，要按任务实际需要准备。Windows 下网页能打开，也不保证所有类 Unix 工具可用；希望复用镜像工具链时优先采用 Linux 容器环境。

### 2.3 使用启动脚本

Linux / macOS：

```bash
chmod +x artex start.sh
./start.sh -addr 127.0.0.1:8787
```

Windows PowerShell：

```powershell
.\start.bat -addr 127.0.0.1:8787
```

访问 [http://localhost:8787](http://localhost:8787)。保持终端运行，按 `Ctrl+C` 正常停止。长期运行可由自己的服务管理器托管启动脚本；Linux 临时后台运行可使用：

```bash
nohup ./start.sh -addr 127.0.0.1:8787 >artex.log 2>&1 &
```

页面更新通过特定退出码请求启动脚本重新拉起。直接执行 `artex` 适合临时诊断，但在线更新后可能没有进程把它重启。

## 3. 从源码运行和编译

### 3.1 前置条件

- Go 工具链满足 [go.mod](https://github.com/fraternity-z/ARTEX/blob/main/go.mod)，当前声明为 **1.26.3**。
- Node.js 22 与 npm，用锁文件执行 `npm ci`。
- 已启动的 PostgreSQL，且 ARTEX 连接配置正确。
- 需要使用的工具安装在真正执行 ARTEX 的环境中。

在仓库根目录检查：

```text
go version
node --version
npm --version
```

只编译不会用到模型 Key，真实运行任务时才需要模型配置。

### 3.2 可选：只用 Compose 启动开发数据库

如果没有现成数据库，可以复用仓库 Compose 的 `postgres` 服务。先按[快速开始](使用手册.md)创建 `.env` 并设置密码。新建本地文件 `docker-compose.dev.yml`：

```yaml
services:
  postgres:
    ports:
      - "127.0.0.1:5433:5432"
```

启动数据库，不启动应用镜像：

```text
docker compose -f docker-compose.yml -f docker-compose.dev.yml up -d postgres
```

在仓库根目录创建 `config.json`，`host` 为 `127.0.0.1`、`port` 为 `5433`，用户、密码和库名与 `.env` 一致，`skill_dir` 可设为 `./skills`。这个连接结构见[高级配置](高级配置.md#config)。

这是本地开发环境，不要让测试和日常实例共用同一个数据库。若你已经有 Compose 部署，上述命令可能操作同一项目的数据库；应使用独立目录和明确的 Compose 项目名隔离开发环境。

### 3.3 开发模式：两个终端

终端 A，在仓库根目录启动后端：

```text
go run ./cmd/artex -addr 127.0.0.1:8787 -proxy 127.0.0.1:8788
```

终端 B，在 `web/` 安装依赖并启动前端：

```text
cd web
npm ci
npm run dev -- --port 5173
```

打开 [http://localhost:5173](http://localhost:5173)。前端将 `/api` 转发到 `http://localhost:8787`。后端没带 `embedui` 标签时不提供内嵌前端，所以直接访问 8787 没有页面并不一定是后端故障；先检查 `/api/health`。

需要改开发后端地址时，设置 `AUTOPENTEST_API` 后再启动前端。使用 Basic Auth 开发时，前后端应保持同一主机名，避免 `localhost` 与 `127.0.0.1` 混用造成 Cookie 问题。

仓库有 `dev.sh` 可同时启动前后端，但它目前没有给 `next dev` 显式传 5173；以 Next 的实际启动输出为准。本手册使用显式端口来避免歧义。退出开发模式需分别停止两个终端。

### 3.4 Linux / macOS / WSL 编译内嵌前端的程序

从仓库根目录开始；如果此前体验过 Mock，先确保本次构建环境没有设置 `NEXT_PUBLIC_MOCK=1`。

```bash
cd web
npm ci
npm run build:static
cd ..
mkdir -p server/webui/dist
cp -R web/out/. server/webui/dist/
CGO_ENABLED=0 go build -tags embedui -o artex ./cmd/artex
./start.sh -addr 127.0.0.1:8787
```

注意复制的是 `out/` **里面的文件**，最终应存在 `server/webui/dist/index.html`，不能多嵌套一层 `dist/out/`。重复构建时还要清理不再使用的旧静态文件，仓库 `build.sh` 使用 `rsync --delete` 完成同步，适合后续重复打包。

`go build` 未注入正式版本号时，程序显示 `dev`，页面更新会禁用；这是预期行为。

### 3.5 原生 Windows PowerShell 编译

`build:static` 脚本采用 POSIX 环境变量写法，在原生 PowerShell 下请改成先设置变量：

```powershell
Set-Location web
npm ci
$env:NEXT_EXPORT = "1"
npm run build
Remove-Item Env:NEXT_EXPORT
Set-Location ..
New-Item -ItemType Directory -Force .\server\webui\dist | Out-Null
Copy-Item .\web\out\* .\server\webui\dist -Recurse -Force
$env:CGO_ENABLED = "0"
go build -tags embedui -o artex.exe ./cmd/artex
Remove-Item Env:CGO_ENABLED
.\start.bat -addr 127.0.0.1:8787
```

开始前同样确认 `NEXT_PUBLIC_MOCK` 未启用。每步成功后再继续；构建失败不能拿以前的 `out/` 当作本次构建成功。重复导出时确认嵌入目录没有残留已删除页面。

### 3.6 打包与本地镜像

具备 Bash、Go、npm、`rsync`、`zip` 的环境可运行：

```bash
./build.sh --target linux/amd64
./build.sh --release
```

前者编译一个目标，后者打包支持的五个平台。默认不用 UPX；需要更小的包时也应先确认运行环境兼容，不能把压缩作为解决启动问题的方法。

仓库 Dockerfile **不是自动编译源码的多阶段构建**，它需要预编译程序位于 `dist/<架构>/artex`。已导出并同步好前端后，例如构建本机 Linux amd64 镜像：

```bash
mkdir -p dist/amd64
CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build -tags embedui -o dist/amd64/artex ./cmd/artex
docker build --platform linux/amd64 --build-arg TARGETARCH=amd64 -t artex:local .
```

ARM64 需同时把目标、目录、构建平台和 `TARGETARCH` 改成 `arm64`，不能只改镜像标签。完成后在 `.env` 设置 `ARTEX_IMAGE=artex`、`ARTEX_TAG=local`，再运行 `docker compose up -d`。本地标签无需向远程仓库拉取。

### 3.7 开发验证的数据库边界

后端测试入口是 `go test ./...`，但其中包含数据库集成测试，部分会清理数据。**不要在连接真实使用数据库的环境直接运行全套测试。** 给测试建立可丢弃的独立 PostgreSQL 数据库，通过 `ARTEX_PG_DSN` 指向它，并留意是否有测试因缺少依赖而跳过。

前端可用 `npx tsc --noEmit` 检查类型，`npm run build` 检查构建，静态发布还应验证导出产物。工具链、测试和生成文件不需要带进日常任务工作空间。

## 4. HTTPS 反向代理

内嵌前端、API 和实时事件流共用 8787。反向代理部署时，把 8787 留在回环或内网，通过 HTTPS 入口访问即可；不需要另外开放一个 SSE 端口。

以下是 Nginx 的结构示例，证书路径和主机名必须替换；它不是自动申请证书的脚本：

```nginx
server {
    listen 443 ssl;
    server_name artex.example.com;
    ssl_certificate     /path/to/fullchain.pem;
    ssl_certificate_key /path/to/privkey.pem;

    location / {
        proxy_pass http://127.0.0.1:8787;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_http_version 1.1;
        proxy_set_header Connection "";
        proxy_buffering off;
        proxy_cache off;
        proxy_read_timeout 3600s;
    }
}
```

此例假设 Nginx 在宿主机运行；Nginx 也在容器中时，`127.0.0.1` 是 Nginx 容器自己，需改成实际可达的应用地址。

SSE 必须关闭缓冲并允许长连接。页面能打开、活动却迟迟不出现时，优先检查缓冲和超时，不要先修改模型参数。默认同源访问无需 `NEXT_PUBLIC_SSE_BASE`；只有明确使用独立事件来源时才考虑它，且它是前端**构建期**变量，容器启动后再加不会改旧静态包。

上传大附件出现反代 413 时，还要核对反代允许的请求大小；即使反代放行，应用自身的大小限制仍然有效。

## 5. 升级与回滚

### 5.1 所有升级先做三件事

1. 查看正在运行的任务、计划、触发会话和审批，安排合适的维护时间。
2. [备份数据库、文件和配置](#backup)，记录当前版本、镜像标签、Compose 项目名和自定义 Skill。
3. 确认目标版本确实有对应平台发布包或镜像，阅读发布说明。

应用启动会幂等执行 schema 迁移，不需要另跑一份手工 SQL。**程序回滚不会自动回退数据库结构**，所以保留旧程序不等于已经具备完整数据回滚能力。

### 5.2 Docker 推荐更新整个镜像

在原部署目录、使用原 Compose 项目名，将 `.env` 中 `ARTEX_TAG` 改成想使用的已发布标签，再执行：

```text
docker compose pull artex
docker compose up -d artex
docker compose ps
docker compose logs --tail=100 artex
```

检查健康接口、登录、任务列表和一份已有报告。`data/`、`skills/` 和数据库卷必须仍指向原来的数据。不要在另一个随意改名的目录重建后，把新空数据库误认为升级丢失数据。

回退程序镜像时，将标签改回记录的旧版本，再拉取、重建应用。若新版本已改变数据库且旧程序不兼容，应按备份恢复流程处理，不能保证单纯换镜像足够。

### 5.3 页面更新适合有启动脚本的程序部署

「系统配置 → 版本与更新」可检查并安装本仓库最新正式 Release。流程包含下载、SHA-256 校验、启动冒烟验证、暂存、退出和由启动脚本重新拉起。

- 检查源为 `fraternity-z/ARTEX`，草稿和预发布不作为正式更新。
- `dev` 或带开发后缀的构建不提供这种更新。
- 更新会中断运行任务，程序回滚也需要重启。
- 保留的 `artex.old` 可用于程序回滚，但不包含数据库回滚。
- Docker 内使用页面更新只换容器可写层的程序，工具链不会更新；重建容器可能回到镜像原版，长期维护仍应更新镜像。

### 5.4 手动替换二进制或源码更新

停掉旧进程，保存旧程序，校验并解压新包，替换程序与需要更新的启动脚本。保留自己的 `config.json`、`data/`、`jwt.key`；自定义 `skills/` 应备份后与新版本逐项合并。

源码更新先检查 Git 状态，保留本地修改，再按源码构建步骤重新生成前端和后端。不要在程序还使用某个可执行文件时强行覆盖它。`install.sh` / `update.sh` 是交互式 Bash 脚本，可以辅助安装/更新；原生 PowerShell 不直接执行 `.sh`，可使用 WSL 或对应手动流程。

## 6. 备份与恢复

### 6.1 一份完整备份包含什么

| 内容 | 为什么需要 |
| --- | --- |
| PostgreSQL 逻辑备份 | 任务、资产、漏洞、设置、模型配置、证据引用等主要数据 |
| 完整 `data/` | 工作文件、流量索引/正文、`evidence/` 证据附件、`archives/tasks/` 冷归档等 |
| `skills/` | 自定义或修改的技能 |
| `config.json`（如使用）、`.env`、Compose 及覆盖文件 | 还原连接、端口和挂载方式 |
| 可执行文件旁的 `jwt.key` | 保留登录签名密钥；没有它恢复后需重新登录 |
| 版本与部署信息 | 程序版本、镜像标签、数据库版本、Compose 项目名、路径 |

只备份数据库会缺附件，只备份 `data/` 会缺主要业务记录。证据正文与 SQL 引用要来自同一一致时间点。任务归档只是本机存储分层，不能代替整机数据备份；复测历史的归档限制见[日常使用](日常使用.md#findings)。

### 6.2 单实例 Compose 备份示例

适用于本仓库默认目录与默认用户/库名 `artex`。如果改过 `POSTGRES_USER` / `POSTGRES_DB`，下面的 `-U` / `-d` 要对应修改。多应用共用数据库时，要确保所有写入方都停止，不能只停其中一个。

先让运行任务暂停并等待当前操作停止，再停止应用容器，数据库保持运行。每条命令都确认成功再继续；失败时保留现场，不要拿不完整备份覆盖上一份好备份。

Linux / macOS / WSL，在部署目录执行：

```bash
artex_backup="../artex-backups/$(date +%Y%m%d-%H%M%S)"
mkdir -p "$artex_backup"
docker compose stop artex
docker compose exec -T postgres pg_dump -U artex -d artex -Fc -f /tmp/artex-manual.dump
docker compose cp postgres:/tmp/artex-manual.dump "$artex_backup/db.dump"
cp -a data skills .env docker-compose.yml "$artex_backup/"
docker compose cp artex:/app/jwt.key "$artex_backup/jwt.key"
docker compose exec -T postgres pg_restore --list /tmp/artex-manual.dump
docker compose start artex
```

Windows PowerShell 使用以下等价流程。数据库二进制备份用 `docker compose cp` 复制，避免通过文本管道或重定向处理：

```powershell
$artexBackup = Join-Path .. ("artex-backups/" + (Get-Date -Format "yyyyMMdd-HHmmss"))
New-Item -ItemType Directory -Path $artexBackup | Out-Null
docker compose stop artex
docker compose exec -T postgres pg_dump -U artex -d artex -Fc -f /tmp/artex-manual.dump
docker compose cp postgres:/tmp/artex-manual.dump "$artexBackup/db.dump"
Copy-Item -LiteralPath @(".\data", ".\skills", ".\.env", ".\docker-compose.yml") -Destination $artexBackup -Recurse
docker compose cp artex:/app/jwt.key "$artexBackup/jwt.key"
docker compose exec -T postgres pg_restore --list /tmp/artex-manual.dump
docker compose start artex
```

如果未完成过成功启动，可能尚无 `jwt.key`；不要因此误以为数据库备份失败。使用了配置文件、其他挂载目录或 Compose 覆盖文件时，另外一起备份。记录版本和项目名，把备份放到受保护的独立存储；数据库备份本身可能包含模型与通知凭据。

`pg_restore --list` 只确认备份目录可读，**真正验证恢复能力需要在隔离环境做一次恢复演练**。应用重新启动后核对任务状态，按需要恢复已暂停的任务。

### 6.3 优先恢复到新的隔离实例

不要直接覆盖目前还能用的实例。选择新机器或全新的目录与 Compose 项目名，准备相同版本的程序/镜像、匹配的 PostgreSQL 主版本，再恢复。以下 Bash 示例假设目标目录与 `artex-restore` 项目都不存在；`artex_backup` 要填写实际**绝对路径**。

```bash
artex_backup="/absolute/path/to/artex-backup"
mkdir ARTEX-restore
cd ARTEX-restore
cp -a "$artex_backup/docker-compose.yml" "$artex_backup/.env" .
cp -a "$artex_backup/data" "$artex_backup/skills" .
```

如有覆盖文件，先复制并检查其挂载和端口。同机演练时，将恢复实例网页映射改成未使用的回环端口（例如 `127.0.0.1:18787:8787`），移除不需要的 8788 映射或换端口。确保没有继续挂载原实例的数据路径。

启动**新实例的空数据库**并恢复：

```bash
docker compose -p artex-restore up -d postgres
docker compose -p artex-restore cp "$artex_backup/db.dump" postgres:/tmp/artex-restore.dump
docker compose -p artex-restore exec -T postgres pg_restore --exit-on-error --no-owner --no-privileges -U artex -d artex /tmp/artex-restore.dump
```

等待数据库健康后再执行恢复。只有空的新数据库才适合直接执行上面步骤；已有同名表导致失败时，先检查是不是用了错误项目，不要加清库参数盲目重试。

恢复副本包含原计划、触发器、模型和通知设置。**先隔离演练环境的外部连接**，避免副本启动后重新执行任务或发送通知。数据库恢复成功后，创建应用容器；若备份有 `jwt.key`，在启动前放回：

```bash
docker compose -p artex-restore create artex
docker compose -p artex-restore cp "$artex_backup/jwt.key" artex:/app/jwt.key
docker compose -p artex-restore start artex
```

没有签名密钥备份时省略对应复制，使用原管理员密码重新登录；如果原实例启用了 HTTP Basic Auth，恢复后也仍需通过该层验证。

Windows 可用 `New-Item` / `Copy-Item` 完成目录准备，后面的 Docker 命令相同，变量改为实际 PowerShell 路径变量。不要把 Bash 的 `$artex_backup="..."` 赋值写法直接贴到 PowerShell。

验收至少包括：登录成功；任务和发现数量合理；一份带流量证据的报告能打开及导出；自定义 Skill 存在；归档可以读取或还原；页面没有附件缺失错误。完成演练后再决定是否切换正式使用入口。

### 6.4 非 Docker 部署

停止 ARTEX 后，使用 PostgreSQL 的 `pg_dump -Fc` 备份实际库，同时复制 `-data` 指向的整个目录、技能目录、配置文件与程序旁的 `jwt.key`。恢复到新库与新目录，修正连接和路径，再启动相同版本程序验收。

不要直接复制一个正在运行的 PostgreSQL 数据目录来代替逻辑备份，也不要只复制正在写入的 SQLite 主文件而漏掉 WAL。无法停机时需要数据库与文件系统协调的一致性快照方案，不能照搬上面的单实例停机步骤。

<a id="password"></a>

## 7. 密码维护

### 7.1 忘记 ARTEX 登录密码

用户名固定为 `ARTEX`。能登录时，通过用户菜单修改密码。忘记密码时，仓库提供 `reset-password.sh`，它连接数据库更新登录密码，不需要删除任务。

在包含脚本的仓库目录，Bash 环境下使用：

```bash
# Compose 部署，按提示输入新密码并确认目标数据库
./reset-password.sh -m docker
```

本地 PostgreSQL：

```bash
./reset-password.sh -m local --config /absolute/path/to/config.json
```

本地模式需要 `psql`；数据库角色需要相应权限，脚本依赖 `pgcrypto`。原生 PowerShell 用户可在合适的 WSL/Bash 环境使用，或由数据库管理员按项目脚本处理。优先使用交互输入，不把新密码写进命令行历史；选择包含密码的 DSN 时也要避免泄露终端输出。

脚本成功后用新密码登录，不需要重置整个系统。数据库密码、ARTEX 登录密码和 HTTP Basic Auth 密码彼此独立。

### 7.2 忘记 HTTP Basic Auth 密码

这层验证可能在登录页出现之前就阻止访问。具备服务器数据库管理权限时，可连接**正确的应用数据库**，关闭独立验证后重启 ARTEX，再正常登录并重新设置：

```sql
UPDATE settings
SET value = jsonb_set(value::jsonb, '{enabled}', 'false'::jsonb)::text,
    updated_at = now()
WHERE key = 'auth.http_basic';
```

这只关闭独立访问验证，不重置 `ARTEX` 登录密码，也不删除任务。

<a id="troubleshooting"></a>

## 8. 故障排查速查表

先判断是哪一层失败：**进程 / 数据库 → 网页与认证 → 模型 → 工具与目标网络 → 记录和报告**。一次只改一个因素，保留原始错误信息。

| 现象 | 优先检查 | 处理方向 |
| --- | --- | --- |
| `docker` 无法连接 daemon | Docker 服务是否运行、当前上下文是否正确 | 启动 Docker，先让 `docker version` 能读到服务端 |
| 镜像 `manifest unknown` / 找不到标签 | 本仓库是否已经发布该标签与平台 | 使用实际已发布标签；没有发布产物时从源码构建 |
| GHCR `denied` / 拉取失败 | 镜像是否公开、网络及登录权限 | 核对仓库 Packages 可见性；不能靠删除本地数据解决 |
| 应用不断重启 | `docker compose logs --tail=100 artex` 和数据库状态 | 先修第一条启动错误，不要只反复重启 |
| `未找到数据库配置` | 配置路径、JSON 格式、`ARTEX_PG_DSN` | 看日志打印的实际配置文件位置；直接运行程序不会自动加载 `.env` |
| 数据库拒绝连接 | 主机、端口、服务状态 | 容器间用 `postgres:5432`；宿主连接需显式发布端口；不要混用 5432/5433 |
| PostgreSQL 密码错误 | 实际数据库角色密码与 `.env` 是否一致 | 已初始化的卷不会因修改 `POSTGRES_PASSWORD` 自动改密码；用旧配置或按数据库方式改角色密码，勿删卷 |
| 网页打不开 / 连接被拒绝 | 8787 是否监听、映射、防火墙、访问主机 | 先在部署机查健康接口，再查浏览器到部署机的路径 |
| 健康检查正常但页面 404 | 是否仅启动了未嵌入前端的 Go 程序 | 开发模式访问 Next 端口；单程序模式重新导出并以 `embedui` 构建 |
| 页面打开仍像演示数据 | 构建/启动时是否有 `NEXT_PUBLIC_MOCK=1` | 清理该环境变量并重建真实前端，不能只重启后端 |
| 初始化页显示无法确认状态 | 后端和数据库是否可用 | 恢复服务再重试，不要删除密码记录重新初始化 |
| 登录失败 | 用户名大写 `ARTEX`、密码、Basic Auth 层 | 按对应密码流程处理；两层凭据不能混用 |
| 重建容器后需要重新登录 | `/app/jwt.key` 是否重新生成 | 正常重新登录；核对任务是否还在，不要直接认定数据丢失 |
| 模型 401 / 403 | Key、服务地址、模型权限 | 修复凭据和权限；增加重试无效 |
| 模型 404 | 模型 ID、API Base URL、接口格式 | 按服务商实际协议设置，测试后保存并激活 |
| 模型 400 / `unsupported_parameter` | 思考字段、输出上限字段、接口兼容性 | 先取消不支持的可选字段，再用最小请求测试 |
| 模型 429 | 普通限速还是明确额度不足 | 限速降并发/请求速率；明确额度不足再充值或切配置链 |
| 模型测试成功但任务无输出 | 是否保存激活、Agent 独立绑定、计划、排队、审批 | 按实际调用链检查，不只看测试按钮 |
| 改全局模型不生效 | Agent 绑定或任务/会话指定 | 按 Agent → 任务/会话 → 全局优先级检查 |
| 活动流延迟，刷新才出现 | 反代缓冲、SSE 长连接、浏览器连接 | 关闭缓冲并调长读取超时；模型非流式时实时反馈也不同 |
| `command not found` / 解释器不存在 | 可执行程序是否在 ARTEX 容器/服务环境中 | 安装必要工具或改正确的服务端绝对路径 |
| MCP 保存了但没有工具 | 传输协议、实际端点、认证、命令参数 | 刷新工具列表，确认启用并授权给 Agent |
| Skill 列表为空 | `skill_dir` 是否误留 `/opt/artex/skills`、挂载是否覆盖 | 查启动日志中的技能绝对路径，确认里面有技能目录和 `SKILL.md` |
| 容器访问不了本机服务/代理 | `127.0.0.1` 是否指错环境、服务是否只监听宿主回环 | 配置容器可达地址和实验网络；不要盲目扩大测试范围 |
| 有请求但流量页为空 | 捕获是否提前开启、代理是否启动、工具是否经过代理 | 用受控 HTTP 请求验证记录链；已错过的请求不能补录 |
| HTTPS 录制证书错误 | 录制 CA 信任、域名与证书、客户端代理配置 | 使用正确 CA；直接访问 HTTPS IP 仍可能有证书限制 |
| 有流量但漏洞没有证据 | 是否人工绑定或开启自动绑定 | 两者独立；先核对真实请求，再关联到正确漏洞 |
| 自动报告 / 历史整理不运行 | Reporter 是否存在、启用、模型可用、触发设置 | 恢复所需配置，检查其会话和排队失败信息 |
| ZIP 导出提示证据缺失或损坏 | `data/evidence` 与数据库是否成套恢复 | 恢复同一时间点完整备份；不要伪造或修改正文绕过校验 |
| 归档按钮不可用 | 是否先暂停、是否被其他任务继承 | 暂停后处理依赖任务，再归档来源任务 |
| 升级后任务像“清空”了 | Compose 项目名、数据库卷、`ARTEX_CONFIG`、挂载路径 | 核对是否连到新空库；找到原卷和原路径，不要继续写入混淆现场 |
| 通知测试成功但没有业务消息 | 渠道开关、最低级别、包含/排除、汇总周期、限流 | 看投递记录和过滤条件，不要反复重建渠道 |
| Windows `NEXT_EXPORT` 不是命令 | 把 POSIX npm 脚本直接在原生 Windows 执行 | 使用本章 PowerShell 先设 `$env:NEXT_EXPORT` 的步骤 |

### 如何最小化复现

出现模型或工具错误时，暂停大任务，用一个本地小文件或单个允许的实验请求复现。必要时只短暂启用 LLM 录制，记录配置名称、时间、任务 ID、工具名称、错误码和脱敏错误文本。确认问题消失后再恢复原任务，避免让大任务重复消耗额度。

## 9. 提交问题前收集什么

在本仓库 [Issues](https://github.com/fraternity-z/ARTEX/issues) 提交问题时，建议使用下面的内容结构：

```text
ARTEX 版本：
部署方式：Compose / Release 二进制 / 源码
系统和 CPU 架构：
期望发生什么：
实际发生什么：
最短复现步骤：
发生时间与相关任务 ID：
错误码及脱敏日志：
是否涉及反代、代理、MCP 或自定义 Agent：
已经尝试过什么：
```

不要直接上传 `.env`、`config.json`、数据库备份、`jwt.key`、完整 Authorization / Cookie 或未脱敏的 LLM 原文。报告中保留定位问题所需的字段与结构即可。提供运行步骤和明确错误，比一张“没有结果”的截图更有助于排查。
