# 文档站维护与发布

文档站和 ARTEX 程序放在同一仓库，分别构建、分别发布。修改手册时直接编辑 `docs/` 中的 Markdown，不需要再维护一份网页副本。

网站使用 VitePress，提供分类导航、中文全文搜索、页内目录、代码复制、明暗主题和手机导航。搜索索引随网站一起生成，在读者浏览器中查询，不需要外部搜索服务。

## 1. 本地预览

准备 Node.js 22 或更高版本。在仓库根目录执行，PowerShell、Bash 均可：

```text
cd docs
npm ci
npm run dev
```

打开终端显示的地址，默认是 `http://127.0.0.1:5173`。该端口如已被 ARTEX 开发前端占用，可执行 `npm run dev -- --port 5174`。编辑 Markdown 后网页自动更新；按 `Ctrl+C` 停止。

检查正式构建：

```text
npm test
npm run build
npm run preview
```

预览地址以终端输出为准，默认端口 `4173`。生成的静态网站位于 `docs/.vitepress/dist/`。需要通过 HTTP 服务预览，不要双击其中的 HTML 文件。

构建只读取文档，不需要运行 Go 后端、数据库或配置模型密钥。

## 2. 发布到 GitHub Pages

仓库已经提供 `.github/workflows/docs.yml`：

- Pull Request 修改文档时，只安装依赖、测试和构建。
- `main` 分支收到文档或文档工作流修改时，构建并发布。
- 也可以在 **Actions → deploy-docs → Run workflow** 手动运行。
- 程序的 Release、镜像和 Demo 仍使用各自原有工作流。

首次启用：

1. 将文档与工作流提交、推送到自己的仓库默认分支。此工作流默认监听 `main`；如果实际默认分支不同，要相应修改。
2. 进入仓库 **Settings → Pages → Build and deployment**。
3. 将 **Source** 设为 **GitHub Actions**。
4. 打开 **Actions → deploy-docs**，运行工作流。
5. 等 `build` 和 `deploy` 都成功后，打开部署任务返回的网址。

普通项目仓库的默认网址形如 `https://<用户名>.github.io/<仓库名>/`。例如当前仓库通常对应 `https://fraternity-z.github.io/ARTEX/`；**是否已经上线，以实际工作流结果与 Pages 设置为准**。

无需额外的发布 Token：工作流使用 GitHub 提供的短期身份与 Pages 权限。若组织策略禁止 Pages 或 Actions，需先由仓库管理员调整对应设置。

## 3. 子路径和自定义域名

`DOCS_BASE` 是**网址中的路径前缀**，不是完整域名。它必须以 `/` 开头和结尾。

| 访问网址 | `DOCS_BASE` |
| --- | --- |
| `https://name.github.io/ARTEX/` | `/ARTEX/` |
| `https://docs.example.com/` | `/` |
| `https://example.com/help/` | `/help/` |

工作流默认使用 `/<仓库名>/`。如果使用自定义域名，或仓库名为 `name.github.io` 的用户站点，到 **Settings → Secrets and variables → Actions → Variables** 添加 `DOCS_BASE`，值设为 `/`。自定义域名还需要在 Pages 设置中绑定、按 GitHub 指引配置 DNS，并启用 HTTPS；修改后重新运行工作流。

本地构建默认使用 `/`。要检查与 GitHub 项目站相同的子路径：

PowerShell：

```powershell
$env:DOCS_BASE = "/ARTEX/"
npm run build
npm run preview
# 退出预览后，清理当前终端变量：
Remove-Item Env:DOCS_BASE
```

Bash：

```bash
DOCS_BASE=/ARTEX/ npm run build
DOCS_BASE=/ARTEX/ npm run preview
```

访问 `http://localhost:4173/ARTEX/`，检查首页卡片、搜索结果和刷新后的页面是否正常。配置了错误前缀时，常见现象是页面没有样式、脚本 404 或内页打不开。

也可把 `.vitepress/dist/` 的**内容**放到其他静态托管平台或自己的 Web 服务器。构建命令为 `npm ci && npm run build`，执行目录是 `docs/`，输出目录是 `.vitepress/dist/`；构建前按实际路径设置 `DOCS_BASE`。

## 4. 平时怎么改文档

| 文件 | 用途 |
| --- | --- |
| `docs/index.md` | 文档首页与阅读入口 |
| `docs/使用手册.md` | 入门、安装、首次设置与练习 |
| `docs/日常使用.md` | 日常操作步骤 |
| `docs/高级配置.md` | 模型、配置和扩展能力 |
| `docs/部署维护与排错.md` | 维护和故障排查 |
| `docs/漏洞流量证据.md` | 已有流量证据技术说明 |
| `docs/.vitepress/config.mjs` | 标题、分类、导航、搜索、发布路径 |
| `docs/.vitepress/theme/style.css` | 品牌色、排版和首页卡片 |

已有章节通过稳定的 HTML 锚点互相链接，例如 `日常使用.md#findings`。修改章节标题时保留这些 `id`，避免侧栏和旧链接失效。

新增页面时：

1. 在 `docs/` 新建 Markdown，使用一个一级标题，然后按步骤分二、三级标题。
2. 在 `.gitignore` 的文档白名单里加入该文件，确保它能被提交。
3. 在 `.vitepress/config.mjs` 的对应分组添加导航。
4. 页间链接使用相对路径，例如 `[高级配置](高级配置.md#llm)`；指向仓库源码时使用完整 GitHub 链接。
5. 运行测试与构建，再在桌面和手机宽度检查导航、代码和表格。

`docs/` 是公开文档源目录。不要在这里放本地笔记、真实日志、账号配置、密钥或业务数据，即使某个文件被 Git 忽略，本地构建仍可能读取它。依赖目录、构建产物和缓存已排除；发布只使用工作流检出的仓库内容。

## 5. 发布问题排查

| 现象 | 先检查 |
| --- | --- |
| GitHub 页面仍显示仓库说明或 404 | Pages Source 是否为 GitHub Actions，deploy 是否成功 |
| 构建失败并提示 dead link | 文档链接的目标文件是否存在；仓库源码链接是否误写成本地网页路径 |
| 页面存在但样式和脚本 404 | `DOCS_BASE` 与访问路径是否一致，修改后是否重新构建 |
| 搜索查不到新内容 | 是否发布了最新构建，浏览器是否仍缓存旧页面 |
| 页面没有最后更新时间 | 文件是否已有 Git 提交；本地新文件没有历史是正常现象 |
| `npm ci` 报锁文件不一致 | 依赖变更后先运行 `npm install` 更新 `docs/package-lock.json`，检查并一并提交 |

涉及框架升级时，先看 [VitePress 官方文档](https://vitepress.dev/zh/guide/what-is-vitepress)，在分支上验证构建、中文搜索和移动端交互，再合并。

当前使用 VitePress 1.6.4；其默认 Vite 5 工具链存在已公开漏洞，因此在 `package.json` 中将 Vite 固定为已修复的 6.4.3。升级时同时检查该覆盖项与 `npm audit`，并重新验证本地预览和正式构建。
